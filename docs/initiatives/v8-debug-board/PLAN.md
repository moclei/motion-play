# v8 Main Board — Debug Board — Plan

## Approach

Four strands, run in sequence in one initiative. They share one board model and one design-intent file.

1. **Power-path investigation (desk → bench → design).** Workers trace v7's battery and power path from the schematic and the datasheets. They root-cause the BQ24195 "needs I²C" fault and rank the mechanisms by which battery connection could cook a board. They then write a bench relay for the Debugger (`debugger/RELAY-power.md`). The Debugger runs the bench work on #0001, #0002 and #0004 as lab cards, outside this initiative. The v8 power design (Phase 7) is gated on those findings (wait **W1**).
2. **v8 design intent and schematic.** One design-intent file, `hardware/pcb-main-v8/CONTEXT.md`, holds every v8 decision: the GPIO allocation, the jumper matrix (with v7 and v8 positions), the test-point and ground-point list, debug LEDs, part choices, and inherited v7 faults with their fixes. The schematic is built from it with the schematic tools. Workers can't do some schematic steps (wiring and Update-PCB-from-schematic are GUI-only today), so those become user steps with exact instructions.
3. **Board model (audit phases 1–2).** `kicad-extraction-audit.md` §5–§6.1 is the spec: one parser and one model, with zones (de-fractured fills), stackup, true pad polygons, bodies, outline, net topology and provenance. Reports are derived from the model: net-centric, plane/region, and per-net PNGs. It is validated on v7 against the audit's fixture table. This model then feeds both the AI layout work and the partner review. It absorbs the queued `pcb-board-model` initiative (decisioning §3.2a row 2) and supersedes the never-run `routing-verification` initiative.
4. **AI layout, learning as we go.** Placement and routing are trialled in small, reviewed steps. Each step follows the same loop: Worker writes a placement or routing with a script, then the user reviews it and corrects it in KiCad. A Worker diffs the user's corrections against what it wrote (board model, before vs after) and turns each correction into a rule in `tools/pcb-context/` (rules config and CONTEXT). The next step runs with the updated rules. Placement goes block by block, then the whole board. Routing is tentative: AI routes the low-risk nets, and the user owns the nets in OQ-1.

Review before ordering = the user's review + an AI partner review answered from board-model output (no throwaway probes), with targeted questions fixed in advance (Technical Notes). DRC/ERC clean. Then fab outputs, preflight (stock, BOM/CPL), user places the order (**W-order**).

**Partner review: targeted questions (Phase 18).** (1) Every member of each SDA/SCL net, its route, neighbours within the audit radii, and reference plane, in each jumper position. (2) What protects each cable-facing line, and where. (3) Battery → charger → boost → LDO path vs the Phase 2/7 failure mechanisms. (4) For each jumper in its v7 position, the net topology matches v7's (schematic level; the copper is new by design). (5) Every test point has a ground point within spring reach. (6) Antenna keepout, USB pair, switching loops.

**Board-model decisions (audit §6.1).** Generated outputs are committed with `_provenance` (tools/CONTEXT.md Source-Hash Rule), beside the PCB in `<kicad folder>/board-model/` (model, net and plane reports, `img/` PNGs), generated from the repo path so `--fresh` can re-hash the source. The stale v7 `pcb-layout-context.json` / `drc-report.json` are marked historical, not deleted (the debug track cites `c2acffc` files). Reads use kiutils + kicad-cli. Board writes go through one write path, chosen in OQ-3 (AI layout tooling below). Definitions (high-current, high dv/dt, neighbour radii, edge-to-edge clearance), plus driver pads and critical nets, go in a per-board config file, `tools/pcb-context/board-config/<pcb stem>.json` (picked up by stem), seeded from audit §6.1. Net topology follows KiCad's connectivity rule: an anchor of one item inside the other's copper.

**AI layout tooling.** Placement logic generalises `place_power.py`. Its write path does not carry over: a kiutils save corrupts a KiCad-saved board (OQ-11), and `place_power.py` already avoids kiutils by rewriting only the footprint's `(at …)` text, which is only right for pure moves (a KiCad 9 board stores pad angles with the footprint's rotation included: on v7 `c2acffc` the TPS61088 footprint is at 90° and its first pad at 270°). All board writes (placement, Phase 16 tracks and vias, zone refill) go through one small writer module chosen in OQ-3. Recommended: KiCad 9.0.4's own `pcbnew` Python module, run with KiCad's bundled Python 3.9 (`/Applications/KiCad/KiCad.app/Contents/Frameworks/Python.framework/Versions/Current/bin/python3`), headless. Planner probe 2026-11-07 on a scratch copy of v7 `c2acffc`: a load + save is byte-identical (793 hide, 469 locked, 19 free, 3,644 uuid all kept); moving, rotating and flipping C9 writes a board that kicad-cli 9.0.4 loads and runs DRC on. Our tools stay on Python 3.7 + kiutils for reading and computing; the writer takes a JSON op list (ref → x, y, rotation, side) and is the only code that imports `pcbnew`. Every write: refuse while a `~*.kicad_pcb.lck` exists (KiCad must have the board closed); afterwards kicad-cli must load the board, and a board-model before/after check must show that only the named footprints moved and the netlist is unchanged. `pcbnew` is removed in KiCad 11 (landscape §4, around early 2027), so the writer stays one module behind a narrow interface, swappable for kicad-python IPC later. The rules config holds constraints that can be checked (keepouts, decoupling distance, test-point spacing, connector edges). Placement runs: board model in → placement → write → board-model check (overlaps, courtyards, rules) → render PNG → user review. The user's corrections are measured as a before/after model diff of positions only, so this needs no diff mode.

**Firmware.** A `motion-play-v8` env with the pin set chosen at build time to match jumper (a), plus a v8 diag image. No v7 env changes.

**Schematic readability (Phases 11a–11f, replan 2026-11-04).** kiutils 1.4.8 doesn't parse KiCad 8/9's `(hide yes)`, so every script load/save of a KiCad-saved sheet unhid its fields (536 on v8), and `annotate.py` put new `ai_*` fields at (0, 0): 1,616 overlapping text pairs (`docs/research/kicad-ai-tooling-2026-11/schematic-readability.md` §1). The fix order: a kiutils shim on every schematic load path plus a lock-file guard on every save (11a, first); a netlist-neutral `tidy_fields.py` pass (11a); `layout_check.py` in the v8 `--check` chain with a per-sheet baseline that only ratchets down (11b); field/label placement rules in `modify.py` for new parts (11b); a netlist-neutral justify pass on the existing labels, which GUI autoplace doesn't move (11c, replan 2026-11-04); the user's GUI autoplace (11c). KiCad 9/10 has no scripted schematic API (KiCad 11) and kicad-cli has no autoplace, so autoplace stays a GUI step. A second-opinion review uses kicad-happy, read-only, from a scratch clone (landscape §5 item 1). User decisions 2026-11-04: keep R66 (10 mΩ, link h4); add a test point (with its GND point) on BAT_CONN; keep the LED currents as designed; a plain-language tour (`hardware/pcb-main-v8/REVIEW-GUIDE.md`) for W3; the power/TCA re-layout is decided at W3a (OQ-10), not planned now.

## Rejected Approaches
- Separate `pcb-board-model` initiative run first: folded in, because v8 layout and review are its only consumer now and the user wants one initiative at a time.
- Targeted review via throwaway kiutils probes only: user wants reusable scripts for partner review.
- Fixing the BQ fault in firmware only (current `configureBQ24195()`): the brief asks for a design root cause.
- Board-model topology joining a track to a pad only when the track endpoint lies inside the pad: split 6 v7 nets that KiCad (DRC: 0 unconnected) treats as connected; replaced by the anchor-inside-copper rule.
- Plane voids computed by subtracting a buffered split channel between fills: left thin slivers reported as voids; replaced by classing an empty region that touches fills of two nets as a split gap.
- Swapping the BQ24195 for a standalone (no-I²C) charger (Phase 1 option 4): rejected in Phase 7, because it takes the BQ off the bus and no jumper position could then rebuild v7's bus membership (row f).
- Regenerating the v8 power sheet with `generate_power_sheet.py` from `power_v8_spec.json` (Phase 10): it would drop the v7 parts the spec leaves out (U9, D1/R1, TP1–TP4, C7/R27 on the LED rail) and every v7 symbol/footprint choice; replaced by an in-place edit (`v8_power_sheet.py`).
- Bare kiutils `Board` writes for `place.py` (OQ-11, Phase 11a): a load + save of a KiCad 9 board drops footprint field state, locks, via `free` and uuids, and kicad-cli 9.0.4 can't load the result.
- Switching from kiutils to kicad-sch-api to escape the `(hide yes)` bug (Phase 11 replan): needs Python 3.10+ and a port of every tool; a 40-line shim fixes it.
- KiCAD-MCP-Server (Avinash1286) autoplace/declutter tools for the tidy: unvetted, source not visible, writes files directly; our own tidy plus a netlist gate instead.
- `layout_check.py` on the prototype probe's geometry (field angle taken as on screen, every label anchored at its start, 0.72 × height per character): differs from KiCad's plot for rotated fields, sheet pins and labels with no justify (drawn centred); replaced by geometry calibrated on kicad-cli SVG plots (Phase 11b).

## Open Questions
- OQ-1 (by Phase 16): which nets AI may route. Default: the user routes switching power (BQ_SW, BOOST_SW loops), the USB pair and battery/high-current paths. AI routes test-point stubs, LEDs, jumpers and the I²C channels, and the user reviews them. Asked with it (moved from OQ-3): may a scratch-copy Freerouting 2.5 experiment (landscape §5 item 2) be tried on the AI net set?
- ~~OQ-2 (by Phase 3): add a second master footprint (e.g. DevKitC-1 headers, or a header for an external S3/SAMD21) behind jumper (e)?~~ Resolved 2026-11-02: no. Jumper (e) is an external-master header behind open solder jumpers only (`hardware/pcb-main-v8/CONTEXT.md` Jumper matrix → Decisions).
- OQ-3 (by Phase 13, asked before Phase 13 is dispatched): how do scripts save changes to a board file, now that a kiutils save corrupts KiCad 9 boards (OQ-11)? Options, with evidence (landscape §2–§4; Planner probe in AI layout tooling):
  1. **KiCad's `pcbnew` Python module (recommended).** Ships with KiCad 9.0.4, runs headless. Round trip byte-identical on v7; move/rotate/flip handled by KiCad's own code; also writes tracks/vias and refills zones (Phases 16–17). Cost: a second interpreter (KiCad's Python 3.9) for one writer module, which extends BRIEF's toolchain constraint line; removed in KiCad 11, so it's for this board on 9.0.4.
  2. **Surgical text edits of the footprint `(at …)` only** (what `place_power.py` does). No dependency, byte-minimal. Right for pure moves only: a rotation must also rewrite every pad's and field's angle, and a flip to the back mirrors the whole footprint and swaps its layers, which is KiCad's math redone by hand. New tracks would be hand-written s-expressions.
  3. **A board shim like `kiutils_k9.py`.** The schematic shim fixed one flag in 135 lines; the board loses a dozen kinds of data (footprint fields in KiCad 7 form, uuid → tstamp, locked, free, unlocked, bold, sheetname/sheetfile, embedded_fonts, plot settings) in an unmaintained library (last release 2024-02). Each missed item is a corrupt board found late.
  4. **KiCad 9 IPC API / kicad-python.** Official and correct, but needs the KiCad GUI open with the API server on for every write, kipy isn't installed (own venv), and calls can time out while KiCad is busy. Doesn't suit unattended Worker runs; revisit at KiCad 11 (headless).
  5. **A writer of our own.** Option 3's work and more, with nothing reused.
  If the answer is not option 1, Phase 13 goes back to the Planner before its task 2.

- ~~OQ-11 (by Phase 13): does a kiutils `Board` round trip of a KiCad 9 board drop `(hide yes)` or other flags, as the schematic one does?~~ Answered in Phase 11a: yes, and worse. A kiutils 1.4.8 load + save of v7's KiCad 9 board (`c2acffc`, scratch copy) writes footprint properties in the KiCad 7 form (key and value only), so all 793 `(hide yes)` flags go, and with them every footprint field's position, layer and effects (silk reference text included).
